## 2. データフロー（目標構成）

1. Cronが有効なdata_collection_targetsを取得する。
2. Edge Functionが地点・カテゴリ・取得間隔に応じて外部APIを呼び出す。
3. API応答を検証し、単位・提供元・対象時刻・取得時刻・データ種別を付与する。
4. environment_snapshotsへ追記保存する。観測値の重複は一意インデックスで防止し、予報履歴は取得時点ごとに保持する。
5. data_collection_runsへ成功・部分成功・失敗と件数を記録する。
6. fishing_trips / catch_recordsと日時・地点を使って照合し、条件別釣果分析に利用する。

この定期取得フローはDDLを追加しただけでは稼働しない。Edge Function、Cron、API接続設定、対象地点登録が別途必要。

## 3. 初期取得間隔

- 基本間隔は60分。
- 30分取得は、提供元の更新頻度・データの変動性・利用制限を確認した項目だけに適用する。
- 1時間ごとの取得は「取得処理の実行頻度」であり、水温・潮流等の新しい実測値が毎回提供される保証ではない。
- 予報データは予報発表時刻と予報対象時刻を分けて保存する。

## 4. データ区分

- observation: 観測/過去再解析等の実績値。qualityで実測方式や再解析を明示する。
- forecast: 予報値。取得時点ごとの予報履歴を保持する。
- model_estimate: モデル推定値。
- manual: 利用者の現場観察。
- unknown: 旧データ等、区分を特定できない値。

実測ブイ等の観測と、過去天気の再解析値は同じobservationとして扱う場合でもqualityで区別し、同じ精度とみなさない。

## 5. 評価処理の責務分離

- 環境評価は風・波・降水等から魚種共通の環境適合度を返す。
- 魚種評価は魚種プロフィールと季節・水温等から魚種別活動期待度を返す。
- 生態プロフィールの根拠が不足する場合、活動期待度はnull（画面では未評価）とする。
- 係数・プロフィールは暫定で、実釣データによる校正は未完了。

## 6. セキュリティ

- ブラウザに置けるのは公開用anon/publishable keyのみ。
- service_role/secret key、API秘密鍵、パスワード、アクセストークンをソース・ログへ含めない。
- 定期取得は信頼できるサーバー/Edge Function側で実行する。
- 環境データの書込権限はservice_roleに限定する。
- 個人テーブルはRLSを有効にし、auth.uid()で所有者を制限する。

## 7. 障害時

- 外部API失敗時も、取得できた他カテゴリのデータは部分成功として保存する。
- 古いデータを最新値のように表示しない。
- 再試行時の重複保存を避ける。
- エラー詳細は秘密情報を除いてdata_collection_runsへ記録する。
